# 手順書（VM側パイプライン）

対象：VM側で完結する後処理（転送受信→検証→文字起こし→合成→要約の push→削除ガード）。
Mac側ツールについては `docs/P3計画.md`（仕様と連携）、`docs/P3実働手順.md`（ビルド・配置・確認の手順）、`mac-app/README.md`（使い方）を参照。
状態と遷移条件の正本は `docs/状態管理.md`。

## データ領域

すべての実行時データは環境変数 `INTERVIEW_DATA_DIR` が指す領域に置く（リポジトリ内には置かない）。環境変数の定義（push 先の `INTERVIEW_NOTES_REPO` を含む）は、正本 `docs/状態管理.md`「データ領域と環境変数」を参照。

```
$INTERVIEW_DATA_DIR/
  state/sessions.json     # セッション状態の永続化
  staging/<session_id>/   # 転送ステージング（検証前。不完全なコピーはここに留める）
  inbox/<session_id>/     # 受信検証済みの音声（処理用一時コピー）
  work/<session_id>/      # 作業用テキスト（文字起こし・合成結果。要約は push 完了まで一時保持）
  log/events.jsonl        # 通知・処理ログ（日付・セッションID・状態・エラー種別のみ）
```

音声フォルダ（inbox）と md の作業場所（work）は分離する。音声をリポジトリに置かないルールは、正本 `docs/状態管理.md`「音声ファイルの配置」を参照。要約の正本は非公開リポジトリの1か所に絞り、push 成功の確認後に作業用コピーを削除する（正本 `docs/状態管理.md`「要約の保存先」）。

## 転送受信と検証

1. 転送は **VM 側からのプル** で行う（方式の正本は `docs/状態管理.md`「転送方式（プル方式）」、実装契約は `pipeline/SPEC.md`「PULL 追加契約」）。Mac→VM 方向の接続は現行構成に存在しないため、Mac 側から送る方式は採らない。
   - 実行：`INTERVIEW_MAC_SSH_COMMAND`（VM→Mac の SSH 実行コマンドへのパス）と `INTERVIEW_MAC_APP_DIR`（Mac 側アプリデータ領域）を設定し、`pull` を実行する。プルは Mac 側のセッション記録から転送待ちを拾い、マニフェストと音声ファイルをステージングへ取得して受信検証まで行う。
   - 運用の並び：`pull` → `run` の順を基本とする（`run` はステージングに残った検証待ち分の検証も担う）。
   - 取得失敗は `transfer_fetch_failed`、検証不一致は `transfer_verification_failed` として未処理に残り、次回プル／ランで再開する。Mac 側の原音声は未処理の間は削除されない。なお、プルで部分取得のまま残ったステージングは、続く `run` が検証対象として拾い、検証失敗（`transfer_verification_failed`）として記録し直す場合がある（未検証ファイルが処理対象に入ることはない）。
2. マニフェスト（JSON）：配置は `staging/<session_id>/manifest.json`。`session_id` と、ファイルごとに `name`／`size`／`sha256` を持つ。系統と話者の対応は、正本 `docs/状態管理.md`「話者マッピング」を参照。
3. 検証：全ファイルについて、ステージング上の実サイズ一致と SHA-256 一致を確認する。1件でも不一致なら転送は未完了として扱う。遷移先・再開先は正本 `docs/状態管理.md` の遷移条件表に従う。検証を通過したファイルだけを inbox へ昇格し、状態を `received` にする。
4. 再プル時はステージングを置き換える。受信検証を通過していないファイルは、処理対象に絶対に含めない（正本 `docs/状態管理.md`「二重処理・二重保存の防止」）。

## 自動取り込み（hook）

- 1日1回、hook `interview-recording-watch`（ポーリング間隔 86400 秒）が Mac 側のセッション記録を確認し、VM 側で未取り込みの確定済みセッション（`recorded`／`transfer_pending`／`needs_reprocess`）があればワーカーを起動する。
- ワーカーは本手順書の並び（`pull` → `run` → 要約作成 → `save-note` → `publish-note`）をそのまま実行し、結果を AI組織チャットへ報告する。取り込みに失敗した場合は無言で終わらせず、異常として同じチャットへ報告する。
- Mac へ接続できない・記録を取得できない場合は検知を保留し、次のポーリングで再確認する（失敗を成功扱いにしない）。

## 処理ラン

- 処理ランは毎回、状態ストアを全件走査し、処理可能な状態（`transferring` の検証待ち、`received`、`needs_reprocess` の再開可能分）を取り上げる。
- 順序は、正本 `docs/状態管理.md`「処理順序」のとおりコードで固定する。
- 訂正・要約の生成は判断部分であり、Claude が担う（パイプラインの自動処理には含めない）。要約が用意できたら、`save-note` で登録して `draft_saved` へ進め、続けて `publish-note` で非公開リポジトリへ push する（push 成功の確認後に `final_saved` へ進み、ローカルの要約コピーは削除される）。本人の確認（照合）は行わない。
- push が完了しない場合は、要約はローカルに保持されたまま `draft_saved` に留まる。失敗はイベントに記録し、異常として報告する。
- 失敗はすべて通知イベントに記録し、セッションを `needs_reprocess` に留める。再試行の扱いは正本 `docs/状態管理.md` を参照（回数上限なし・毎ランの全件走査対象）。

## 保存ガード（要約の登録・push前）

登録・push の各処理は、実行前に次のすべてをコードで確認する。1つでも満たさなければ中止し、通知する。

1. 登録する要約ファイルに音声・動画ファイルが含まれていないこと（音声だった場合は登録を中止し、`needs_reprocess` とする）。対象拡張子は、正本 `docs/状態管理.md`「保存ガードの拡張子リスト」のとおり。
2. push 先が非公開リポジトリであること。push の直前に `guards.check_note_destination` が宛先リポジトリの可視性を確認し、private でない・確認できない場合は push しない（公開リポジトリへ要約を上げない）。

push 済みでない要約は削除しない。ローカルコピーの削除は、push 成功をリモート上の内容一致で確認できた場合に限る（`publish.publish_note` がこの順序を固定する）。

## 削除ガード

- VM側コピーの削除：正本 `docs/状態管理.md`「削除の条件」のとおり、処理完了（`processing` を正常終了している）**かつ** 要約の生成確認（`draft_saved` 以降の状態で、`draft_saved_at` が記録されている）の両方を満たす場合のみ、削除コマンドが実行する。満たさない場合は拒否して理由を記録する。削除後は `vm_copy_deleted_at` を記録する。
- Mac側コピーの削除可否判定：正本 `docs/状態管理.md`「削除の条件」のとおり、要約が非公開リポジトリへ push 済み（`final_saved` 以降で、`note_published_at` が記録されている）**かつ** 未処理でないこと（`needs_reprocess` でないこと）を満たすセッションのみ「削除可」。期限（最長7日）は「いつまでに消すか」の上限であり、削除の許可条件ではない。判定はコードが行い、Mac側の実行は Mac 側の工程で行う（本手順書の範囲は判定まで）。
- Mac側コピー削除完了の申告：Mac 側で削除が完了したら、`report-mac-deleted <session_id>` で VM 側へ申告する。VM 側は受付直前に削除可否を再確認し、満たさなければ拒否する。受け付けたら `mac_copy_deleted_at` を記録し、VM側コピーの削除完了も記録済みなら `closed` へ進める。申告は冪等で、再申告しても初回の記録時刻は変わらない。
- 期限管理：正本 `docs/状態管理.md`「削除の条件」のとおり、録音から7日を超え、かつ `final_saved` に到達していないセッションは、削除ではなく「期限超過の未処理」として走査で可視化する（再処理の拾い直しと可視化のため）。

## STTエンジン

- 文字起こしは VM 上の faster-whisper で行う（契約は `pipeline/SPEC.md`「V1 追加契約」）。
- **実行環境（必須）**：faster-whisper は VM のシステム python3 には入っておらず、venv `~/workspace/stt-bench/.venv` の python にある。パイプラインの `run` は必ずこの venv の python で実行すること（例：`~/workspace/stt-bench/.venv/bin/python -m interview_pipeline run`）。システム python3 で実行すると faster-whisper が見つからず実行が失敗する。
- モデルは環境変数 `INTERVIEW_STT_MODEL` で指定する。未設定の場合はエンジン未接続として扱う（未設定時の扱いは、正本 `docs/状態管理.md`「STTエンジン未接続時の扱い」を参照）。
- モデルは `large-v3-turbo` とする。
