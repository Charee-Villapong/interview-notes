## F1：二系統キャプチャの試作方針

標準部品のみで構成し、外部ドライバや仮想オーディオデバイスは導入しない。

| 系統 | 第一候補 | 代替候補 | 備考 |
|---|---|---|---|
| システム音声（相手） | ScreenCaptureKit（`SCStream`、`capturesAudio` 有効） | Core Audio プロセスタップ（`CATapDescription`） | 映像は最小サイズに絞り、音声サンプルだけをファイルへ書く。代替候補は OS バージョン要件が新しいため、第一候補の安定性を実測してから判断する |
| マイク（自分） | AVAudioEngine（入力タップ） | AVCaptureSession | 権限リクエストとレベル取得が素直な第一候補を採る |

- 書き出し形式は両系統とも `.m4a`（AAC、48kHz、モノラル）に統一する。ファイル名は `system_<session_id>.m4a`／`mic_<session_id>.m4a` とし、接頭辞による系統分類（P1 の契約）に一致させる。分類外のファイル（接頭辞が `system`／`mic` のどちらでもないもの）をセッションフォルダに作らない。
- 判断ポイント（F1 実測で確定する）：連続録音の安定性（欠落ゼロが合格ライン）、相手側の音声が出力から消えないこと（ミュートされない設定の確認）、CPU・メモリ負荷、無音区間のレベル実測（自動停止の閾値校正）。
- 自動停止後の再開に備え、猶予中はファイルを開いたままにする方式を雛形の実装とする（再開時はそのまま書き足し、猶予が過ぎれば停止として確定する）。ファイル確定後の再開が必要になる場合は、同一ファイルへの追記（AAC への追記可否）を F1 で検証する。ファイルは常に系統ごとに1本に保つ（複数ファイルに分けると、VM 側の話者合成で時系列のオフセットが失われるため避ける）。

## 必要権限とエンタイトルメント

| 対象 | 仕組み | 必要なもの |
|---|---|---|
| マイク | TCC（Microphone） | `Info.plist` の `NSMicrophoneUsageDescription`。初回利用時に許可ダイアログが出る |
| システム音声（ScreenCaptureKit） | TCC（Screen Recording） | システム設定「プライバシーとセキュリティ > 画面収録」への追加。映像は使わないが、音声キャプチャもこの許可の対象になる |
| システム音声（プロセスタップ採用時） | TCC（System Audio Recording） | `Info.plist` の `NSAudioCaptureUsageDescription` が要る場合がある（F1 で要否を確認） |

- エンタイトルメント：App Sandbox を有効にしないローカル配布の前提では、上記のためのエンタイトルメントは原則不要（マイク用の `com.apple.security.device.audio-input` はサンドボックス配下でのみ必要）。F1 の初回ビルドで `codesign -d --entitlements - <app>` の出力が空（または想定どおり）であることを確認し、判断を確定する。
- 署名と TCC の同一性：アドホック署名のまま再ビルドすると、バイナリの同一性が変わり、付与済みの TCC 許可が失われる既知の落とし穴がある。対策として、バンドル ID を初回ビルド前に確定し、識別子ベースの指定要件（designated requirement）で署名する。再ビルド後に許可が維持されることを、実働段階の確認項目に入れる。
- 確認方法（実働段階）：初回起動でマイク許可ダイアログが出ること／画面収録のリストにアプリが現れること／許可後に両系統の短時間録音が成功すること／再ビルド後も許可が維持されること、を順に確認する。

## Mac側セッション状態と VM側12状態の対応

Mac ツールはセッションごとにメタデータ（JSON）を持ち、`state` フィールドには常に VM 側12状態の語彙だけを入れる。録音中などの Mac 内側の細かい状態は別フィールド `local_phase` に分離し、正本の状態語彙を汚さない。

| Mac側の出来事 | `local_phase` | `state`（VM語彙） | VM側との同期 |
|---|---|---|---|
| 録音開始 | `recording` | （未登録。録音完了まで VM に送らない） | なし |
| 録音中・無音が続く | `recording`（無音タイマ作動） | 同上 | なし |
| 自動停止→猶予中 | `grace` | 同上 | なし |
| 猶予内に再開 | `recording` | 同上 | なし |
| 手動停止／猶予経過／3時間到達で録音確定 | `finalizing` | `recorded` | ローカル確定のみ |
| 転送待ち（確定直後） | `ready_to_transfer` | `transfer_pending` | なし（VM 側プルが拾う） |
| 転送中（VM 側プルが取得中） | （Mac 側は変化なし） | `transferring` | VM 側プルが Mac の録音置き場から取得 |
| VM の受信検証に成功 | `uploaded`（プル後に VM 側状態を写す際） | `received` | VM 側 `receive` 相当（プル工程内の受信検証）の成否で判定 |
| 取得・検証に失敗 | `upload_failed` | `needs_reprocess`（resume: `transfer_pending`） | 次回プルで再開する |
| VM 側で処理が進んだ後 | `mirrored` | VM の現在状態を写す | `status` 照会で取得（削除判定の前に都度照会） |
| 削除可（VM 照会で確認） | `deletion_ready` | `deletable` 相当 | `mac-eligible` の終了コードで判定 |
| Mac 側コピーの削除完了 | `deleted` | `closed`（両側削除が揃った時点） | 申告手段は連携事項（下記） |

## 転送フロー（プル方式。本人の設計変更決定 2026-11-08）

当初は Mac から VM へプッシュする前提だったが、Mac→VM 方向の SSH 接続が現行構成に存在しないことが実測で判明したため（VM 側は外向き接続専用で受信しない）、**VM 側が Mac から取得するプル方式**へ変更した。方式の正本は `docs/状態管理.md`「転送方式（プル方式）」、VM 側の実装契約は `pipeline/SPEC.md`「PULL 追加契約」。セッション ID・マニフェスト・状態・削除ガードの契約はプッシュ前提の P1 から変えていない。

1. セッション ID を面談日付ベースで採番する（`YYYY-MM-DD_NN`。同日の件数はローカルメタデータで数える）。
2. 録音確定後、2ファイルについて `name`／`size`／`sha256` を計算し、マニフェスト（`manifest.json`）を生成する。形式は P1 の `Manifest` と同一とする。Mac 側はここまでで転送待ち（`transfer_pending`）に留まる（自動プッシュは設定 `autoTransferEnabled=false` で無効化し、エラー表示・再試行を行わない）。
3. VM 側のプル工程が、Mac 側セッション記録の一覧から転送待ちを拾い、マニフェストと音声2ファイルを VM のステージング `<data領域>/staging/<session_id>/` へ取得する。取得済み（VM 側で `received` 以降）は再取得しない。
4. VM 側が全ファイルのサイズ＋SHA-256 を照合し、一致した場合のみ inbox へ昇格して `received` になる。取得失敗は `transfer_fetch_failed`、検証不一致は `transfer_verification_failed` として未処理に残し、次回プルで再開する。
5. 接続先・配置先などの環境依存値は、すべて環境変数またはローカル設定ファイル（gitignore 済み）から読む。コードと文書に実値を書かない。

（旧プッシュ手順——Mac 側の `TransferClient` による register／scp 配置／receive 要求——は、プル方式への変更に伴い運用では使わない。コードは設定で有効化できる形で残すが、現行構成では接続自体が成立しない。）

## 削除ガードとの連携

- Mac 側コピーの削除は、VM の CLI `mac-eligible <session_id>` が可（終了コード 0）を返したセッションに限る。判定条件の正本は `docs/状態管理.md`「削除の条件」（確定版保存済み かつ 未処理でないこと）であり、Mac 側で条件を再解釈しない。
- 期限超過の未処理（録音から7日超・`final_saved` 未到達）は、削除のためではなく可視化のために一覧へ挙げる（正本どおり）。未処理は日数に関わらず削除しない。
- 連携事項（未整備）：VM 側の `mac_copy_deleted_at` を記録し `closed` へ進めるための申告手段は、現行 CLI に無い。P3 実働段階で、VM 側工程と合意して CLI 拡張（例：Mac 側削除完了の申告コマンド）を追加する。それまでは Mac 側メタデータに削除完了を記録するに留める。

**修正したもの**：

- `build.sh` のエンタイトルメント表示が標準エラー側への出力である点を踏まえ、出力を潰さない形に修正（確認自体が目的の行だった）。

**初回ビルドで要確認の箇所（この VM に Swift ツールチェインが無く、コンパイル確認は初回ビルドが最初になる）**：

1. 型・API 名の最終確認はビルドエラーの有無で確定する。エラーが出たら実働セッションの場で直す。
2. `SystemAudioCapture` の CMSampleBuffer→AVAudioPCMBuffer 変換（インターリーブ有無とチャンネル配置）。コード内の TODO(F1) のとおり、実サンプルで確定する。
3. `MicCapture` の書き出し（サンプルレートは入力デバイス追随。F1 方針の 48kHz 統一との差は、変換の要否を実測で確定する）。→ **確定・修正済み（2026-11-08 実働セッション）**：この Mac のマイク入力は 16kHz であり、16kHz の AAC に `AVEncoderBitRateKey` を指定すると `AVAudioFile` 生成が `AudioConverterSetProperty(kAudioConverterEncodeBitRate)` の失敗（560226676 '!dat'）で落ち、録音開始がエラーになった（実機で再現し、SR・チャンネル・クライアント形式・ビットレート有無を切り分け済み）。書き出しは共通部品 `AudioFileWriter` で 48kHz・モノラル・64kbps に統一し、入力バッファは `AudioFormatConverter` で変換してから書く形に修正（システム音声側も同じ部品に統一）。実測では 16kHz 入力→変換→AAC 書き出しが正常に通ることを確認済み。
4. `RecordingController`：システム音声の開始が非同期に失敗した場合、マイク停止とエラー表示は行うが、状態（録音中表示・タイマ）の巻き戻しをしていない。要修正候補として、初回ビルド時に併せて直す。→ **修正済み（2026-11-08 実働セッション）**：`rollbackFailedStart` でタイマ停止・セッション情報の消去・作りかけフォルダの除去・待機中への復帰までを巻き戻す。
5. `TransferClient` の出力読み取り（プロセス終了後にまとめて読む方式）。リモート出力が大きい場合にパイプバッファで詰まる余地がある。実働の出力は小さい見込みだが、ダミー転送で確認する。
6. `TransferClient.upload` の scp 宛先に含めた引用（`host:'path/'` 形式）。リモートシェルの解釈次第でパスが壊れる余地がある。ダミー転送で最初に確認し、失敗したら引用を外す形に直す。
