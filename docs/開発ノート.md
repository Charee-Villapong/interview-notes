## V1 実測結果（2026-11-08）

同一の正解テキスト付き日本語音声（system 64.9秒＋mic 116.5秒＝計181.4秒）・同一条件（faster-whisper 1.2.1／ctranslate2 4.8.5／CPU 4スレッド／int8／language=ja／beam_size=5／vad_filter=False）で3モデルを実測した。生データは計測環境（stt-bench）の results に JSON で保存。

| モデル | CER system | CER mic | CER 合計 | RTF | ロード | ピークRSS |
|---|---|---|---|---|---|---|
| medium | 0.48% | 1.53% | 1.16% | 0.770 | 17.7秒 | 1,788MB |
| **large-v3-turbo** | **0.48%** | **0.51%** | **0.50%** | **0.703** | 22.7秒 | **1,623MB** |
| large-v3 | 0.48% | 8.40% | 5.65% | **1.251** | 23.4秒 | 3,176MB |

暫定ライン（CER 10%以下／RTF 1.0以下＝処理時間が面談時間の1倍以内）との照合：

- medium：全項目クリア
- large-v3-turbo：全項目クリア。精度・速度・メモリの全てで3候補中最良
- large-v3：**RTF 1.251 でライン超過**（60分面談で約75分かかる）。mic の CER 8.40% も劣後（発話の脱落と末尾の幻覚を確認）。ピークRSS 3.2GB は共用VM（7.7GB）でも重い

**確定モデル：large-v3-turbo**（2026-11-08 に本人が確定）。パイプライン接続はこのモデルで実施済み：

- `FasterWhisperTranscriber` を実装し、CLI の `run` が環境変数 `INTERVIEW_STT_MODEL` で実エンジンを使うよう配線（未設定時は従来どおり未接続扱い）。契約は `pipeline/SPEC.md`「V1 追加契約」
- 実働確認：実モデル＋計測用音声で CLI `run` を実行し、セッションが `awaiting_editing` まで進み、話者ラベル付き transcript.md が生成されることを確認（音声181秒に対し全体約139秒）

## P2（Google連携）の実装計画（2026-11-08）

範囲：カレンダー検知→検知レジストリ→Docsノート／Sheets面談一覧→リマインド登録。契約は `pipeline/SPEC.md`「P2 追加契約」、手順は `docs/手順書.md`「Google連携（P2）」。

1. 検知：Google Calendar を走査し、自己登録予定はタイトルの主キー（「面接」）、副キー（「面談」）で、招待予定はタイトル・説明文のキーワードで判定する。キーワードはすべてローカル設定で持つ（コードに固定しない）。
2. 検知レジストリ：録音セッションの状態管理とは分離した永続レコード（イベントID冪等）。セッションIDは正本の採番規則で採番し、既存セッションとの衝突を避ける。未録音の予定を `recorded` として `SessionStore` へ登録しない（状態の意味を守るため）。
3. Docs／Sheets：ノートはテンプレート複製＋基本情報プレースホルダ置換で作成し、一覧へはリンク付きで1行追加する。どちらも未実施分だけを補う冪等動作にする。
4. リマインド：判定（前日／当日午前／当日午後）と定型文生成・送信済み記録をコード化し、定期実行（毎日9時・18時）は新規 cron として登録する。
5. テストは Google 接続をゲートウェイのフェイクで切り分け、単体で実行できる形にする。テスト係は仕様（SPEC・正本）のみから先行作成し、実装→独立QA→push前検閲の順で進める。

### P2 着手時点で判明した論点（独断せず報告する）

- 自己登録予定の主キーは「面接」だが、実在の自己登録予定には「面談」とだけあるものがあり、主キーだけでは検知できない。副キー（「面談」）を設定可能にしたうえで既定で有効とし、厳密運用（主キーのみ）へは設定変更だけで戻せる形にした。最終判断は本人に上げる。
- 招待予定の判定キーワードの具体的な集合は企画書で未定義のため、設定で変更可能な既定値として実装する。
- 企業名はタイトル等の決まった書式が無いため、抽出はベストエフォート（括弧内先頭要素など）とし、取れない場合は空欄のままにする（推測で埋めない）。一覧の企業列は後から本人が直せる前提とする。
- QA観察事項への対応：保存ガードのチェック対象は「この保存で配置する全ファイル」と SPEC 文言を確定（手順書の「保存対象」は無限定な文言だったため、C-126 で実態に合わせて「この保存で配置するファイル（現行はドラフト本体1件）」へ揃えた）。第二の防壁として音声・動画拡張子は `.gitignore` でも除外

## 転送方式のプル化（本人の設計変更決定。2026-11-08）

- 経緯：P3 実働セッションで、Mac→VM 方向の SSH 接続が現行構成に存在しないことが実測で判明した（VM 側 Tailscale は外向き専用で受信せず、VM に sshd は無く、Mac→VM 22番は接続不可。Mac に ~/.ssh/config も無い）。動く方向は VM→Mac のみ。本人が「転送はプル方式に変えて進める」と決定した。
- 変更内容：VM 側に `pull.py`（MacSource プロトコル＋SshMacSource 実装＋pull_pending）と CLI `pull` を追加。Mac のセッション記録から転送待ちを拾い、マニフェスト→音声の順にステージングへ取得し、既存の `verify_and_promote` で照合する。失敗の種別として `transfer_fetch_failed` を追加し、検証不一致（`transfer_verification_failed`）と区別する。Mac 側は設定 `autoTransferEnabled`（運用では false）で自動プッシュを止め、録音確定時は転送待ちの記録に留めてエラー表示・再試行をしない形にした。再ビルド・差し替え手順は `docs/P3実働手順.md` の G 節。
- 実地検証（2026-11-08、実経路 VM→Mac）：テスト用セッション（実在の面談と混同しない ID `2099-12-31_99`／`_98`、短いダミー音声2ファイル＋マニフェスト）を Mac の録音置き場に置いて確認した。正常系は pull→照合→inbox 昇格まで通り、inbox のバイト列が Mac 側原本と一致。ハッシュ不一致の _98 は `needs_reprocess`（transfer_verification_failed）として隔離され、正常系を止めなかった。2回目の pull では _99 は skipped（再取得なし）、_98 は再試行されて同じく失敗（再開可能性を確認）。検証後は Mac 側のテストセッションと VM 側の検証用データ領域を片付け、Mac 側は元の状態（config.json のみ）に戻した。
- 残件：プルの定期実行への組み込み方（V3 の運用確定）は未決定。Mac 側の VM 状態ミラーと削除可否照会（旧プッシュ前提の SSH 照会）はプル方式では未整備で、照会できない間は削除不可として fail-closed（安全側）に倒れる。
