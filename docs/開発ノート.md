## P2（Google連携）の実装計画（2026-11-08）

範囲：カレンダー検知→検知レジストリ→Docsノート／Sheets面談一覧→リマインド登録。契約は `pipeline/SPEC.md`「P2 追加契約」、手順は `docs/手順書.md`「Google連携（P2）」。

1. 検知：Google Calendar を走査し、自己登録予定はタイトルの主キー（「面接」）、副キー（「面談」）で、招待予定はタイトル・説明文のキーワードで判定する。キーワードはすべてローカル設定で持つ（コードに固定しない）。
2. 検知レジストリ：録音セッションの状態管理とは分離した永続レコード（イベントID冪等）。セッションIDは正本の採番規則で採番し、既存セッションとの衝突を避ける。未録音の予定を `recorded` として `SessionStore` へ登録しない（状態の意味を守るため）。
3. Docs／Sheets：ノートはテンプレート複製＋基本情報プレースホルダ置換で作成し、一覧へはリンク付きで1行追加する。どちらも未実施分だけを補う冪等動作にする。
4. リマインド：判定（前日／当日午前／当日午後）と定型文生成・送信済み記録をコード化し、定期実行（毎日9時・18時）は新規 cron として登録する。
5. テストは Google 接続をゲートウェイのフェイクで切り分け、単体で実行できる形にする。テスト係は仕様（SPEC・正本）のみから先行作成し、実装→独立QA→push前検閲の順で進める。

### P2 着手時点で判明した論点（独断せず報告する）

- 自己登録予定の主キーは「面接」だが、実在の自己登録予定には「面談」とだけあるものがあり、主キーだけでは検知できない。副キー（「面談」）を設定可能にしたうえで既定で有効とし、厳密運用（主キーのみ）へは設定変更だけで戻せる形にした。最終判断は本人に上げる。
- 招待予定の判定キーワードの具体的な集合は企画書で未定義のため、設定で変更可能な既定値として実装する。
- 企業名はタイトル等の決まった書式が無いため、抽出はベストエフォート（括弧内先頭要素など）とし、取れない場合は空欄のままにする（推測で埋めない）。一覧の企業列は後から本人が直せる前提とする。
- QA観察事項への対応：保存ガードのチェック対象は「この保存で配置する全ファイル」と SPEC 文言を確定（手順書の「保存対象」は無限定な文言だったため、C-126 で実態に合わせて「この保存で配置するファイル（現行はドラフト本体1件）」へ揃えた）。第二の防壁として音声・動画拡張子は `.gitignore` でも除外
